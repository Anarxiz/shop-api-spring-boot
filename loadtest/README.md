.\loadtest\run.ps1 -Profile baseline -Workload mixed -Rate 10 -SkipBuild# Нагрузочное тестирование Shop API

Нужен Docker с Compose и один из вариантов запуска: PowerShell или Bash с `curl`.
k6 запускается в контейнере. Команды выполнять из корня проекта.

## Быстрый старт

```powershell
.\loadtest\run.ps1 -Profile smoke -Workload mixed
```

В Bash (в том числе Git Bash):

```bash
bash loadtest/run.sh --profile smoke --workload mixed
bash loadtest/run.sh --profile baseline --workload mixed --rate 10 --skip-build
```

Параметры Bash: `--profile`, `--workload`, `--rate`, `--users`, `--skip-build`.
Справка доступна через `bash loadtest/run.sh --help`.

Скрипт собирает приложение, поднимает отдельный Compose-проект `shop-loadtest`,
ждёт API, добавляет 20 категорий и 500 доступных блюд, запускает k6 и сохраняет
вывод в `loadtest/results/*.log`. Первый запуск требует скачивания образов.
Повторно можно добавить `-SkipBuild`, если код приложения не менялся.

- Swagger отдельного стенда: http://localhost:18080/swagger-ui.html
- Prometheus отдельного стенда: http://localhost:19090
- Существующее приложение на `8080`, его PostgreSQL и Prometheus на `9090`
  не используются. Не меняйте имя Compose-проекта и не задавайте внешние volumes.

В `loadtest/compose.yml` задано `APP_RATE_LIMIT_ENABLED=false`. Это то же
переопределение `app.rate-limit.enabled=false`, что и в интеграционных тестах.
Основной `application.yaml` не меняется. Лимит отключён только на этом стенде,
чтобы k6 не измерял постоянные 429 вместо производительности API.
Email не настроен; смена статуса и доставка уведомлений в эти сценарии не входят.

Чтобы повторить замер с кэшем каталога Redis, добавь `-Redis` в PowerShell
или `--redis` в Bash. Лимит входа остаётся отключённым на нагрузочном стенде.

```powershell
.\loadtest\run.ps1 -Profile baseline -Workload mixed -Rate 125 -Redis
```

Для сравнения используй те же ресурсы и начальный объём данных. Сопоставь
задержки каталога, вызовы репозиториев и `shop_catalog_cache_lookups_total`.
Для остановки стенда с Redis используй оба файла Compose:

```powershell
docker compose -p shop-loadtest -f loadtest/compose.yml -f compose.redis.yml down
```

## Набор прогонов

| Профиль | Нагрузка | Для чего |
| --- | --- | --- |
| `smoke` | 1 итерация/с, 30 секунд | Проверить сценарий и данные |
| `baseline` | 2 минуты разгона, 5 минут на RATE, 1 минута снижения | Измерить обычную нагрузку |
| `stress` | Рост до RATE, 2×, 4×, 8× по 2 минуты; затем 2 минуты снижения | Найти предел |
| `spike` | Разгон, быстрый скачок до 5× RATE и возврат | Проверить восстановление после пика |
| `soak` | 2 минуты разгона, 30 минут на RATE, 1 минута снижения | Найти утечки и деградацию со временем |

Прогоны выполнять последовательно, начиная с малого RATE:

```powershell
.\loadtest\run.ps1 -Profile smoke -Workload mixed
.\loadtest\run.ps1 -Profile baseline -Workload catalog -Rate 10 -SkipBuild
.\loadtest\run.ps1 -Profile baseline -Workload mixed -Rate 10 -SkipBuild
.\loadtest\run.ps1 -Profile baseline -Workload login -Rate 2 -SkipBuild
.\loadtest\run.ps1 -Profile stress -Workload mixed -Rate 10 -SkipBuild
.\loadtest\run.ps1 -Profile spike -Workload mixed -Rate 10 -SkipBuild
.\loadtest\run.ps1 -Profile soak -Workload mixed -Rate 10 -SkipBuild
```

После stress/spike сначала дождаться восстановления задержек и ошибок до исходного
уровня. Проверять результат каждого прогона, прежде чем увеличивать нагрузку.
Для серьёзного soak после пробного получасового прогона увеличить выдержку до 2–4 часов:

```powershell
docker compose -p shop-loadtest -f loadtest/compose.yml run --rm --no-deps k6 run --summary-mode full -e PROFILE=soak -e WORKLOAD=mixed -e RATE=10 -e SOAK_DURATION=2h /scripts/shop.js
```

Токены действуют 180 минут по основной конфигурации: для прогона дольше этого
нужно добавить обновление токенов или увеличить expiry только на нагрузочном стенде.
Для долгого soak также оценить рост таблицы заказов и размер истории пользователя.

## Что делают сценарии

- `catalog`: чтение категорий, списка блюд, блюда по ID и блюд категории.
- `mixed`: примерно 70% итераций читают каталог, 20% создают заказ, читают его
  и историю заказов, 10% выполняют вход.
- `login`: вход существующих пользователей, включая проверку пароля и создание JWT.

Для `mixed` и `login` setup создаёт 20 пользователей, выполняет вход, для `mixed`
добавляет адреса. Число пользователей можно изменить: `-Users 100`. Проверяются
статусы, наличие токена, ID заказа, сумма и размер первой страницы истории (до 20 заказов).
Данные пользователей/заказов накапливаются; автоматического удаления после теста нет.
Один и тот же пользователь может участвовать в нескольких параллельных итерациях.
Это модель общего потока API, а не точная имитация индивидуальных браузерных сессий.

**RATE — число итераций в секунду, а не число HTTP-запросов или пользователей.**
Для catalog/login одна итерация делает один запрос, для заказа — три. При mixed
ожидается около 1,4 HTTP-запроса на итерацию; фактические RPS смотреть в `http_reqs`.
Темп задаёт arrival-rate executor; дополнительного `sleep()` нет.
Стартует 30 виртуальных пользователей, максимум 100. При необходимости изменить
через `-e PRE_ALLOCATED_VUS=100 -e MAX_VUS=300` в прямой команде k6.

## Критерии и разбор результатов

Начальные пороги в `shop.js` — пример требований, их нужно согласовать с задачей:

- p95 HTTP-задержки < 500 мс, p99 < 1000 мс;
- HTTP-ошибки и неуспешные бизнес-сценарии < 1%;
- p95 полного сценария < 1500 мс;
- `dropped_iterations = 0`: генератор смог запустить все запланированные итерации.

При нарушении порогов k6 возвращает ненулевой код. Если более 10% сценариев
завершаются ошибкой, тест прерывается (проверка начинается спустя 30 секунд).
В stress достижение порога означает найденную границу, а не обязательно дефект.
Смотреть также разбивку HTTP-метрик по `name` в полном отчёте: быстрый каталог
не должен скрывать медленное создание заказа. ID и токены в метки не добавляются.
Setup исключён из HTTP-порогов с помощью метки `phase=load`. Общие HTTP-счётчики
отчёта могут включать setup. Итоговые перцентили охватывают разгон и снижение;
показатели устойчивого режима анализировать в Prometheus по интервалу выдержки.

Во время прогона открыть Prometheus на `19090` и использовать
[готовые PromQL-запросы](../monitoring/README.md): RPS, p95/p99, 5xx, CPU, heap,
GC, активные и ожидающие соединения HikariCP. Сопоставлять временные интервалы.
Через `docker stats` следить также за CPU/памятью k6, PostgreSQL и приложения.
`dropped_iterations` может означать нехватку VU или ресурсов генератора, а не
только предел приложения. Для точных замеров запускать генератор на другой машине.

Приложению выделено 2 CPU, 1 ГБ памяти, heap 512 МБ. Записывать для каждого прогона:
commit, размер данных, ресурсы Docker/CPU, профиль, workload, RATE, USERS,
достигнутые RPS, p95/p99, ошибки, dropped iterations и наблюдаемый предел ресурсов.
Повторить базовый прогон 3 раза с одинаковыми данными; сравнивать медиану результатов.
Для воспроизводимости очищать **только отдельный стенд** и заново загружать seed.
На одном ноутбуке все контейнеры делят ресурсы, поэтому результат характеризует эту среду.

## Остановка и очистка

Остановить отдельный стенд с сохранением тестовых данных:

```powershell
docker compose -p shop-loadtest -f loadtest/compose.yml down
```

Сбросить его БД и историю Prometheus (все данные этого стенда будут удалены):

```powershell
docker compose -p shop-loadtest -f loadtest/compose.yml down -v
```

Отдельно проверить защитный rate limit на стенде с включённым свойством:
запросы сверх лимита должны получать 429 и Retry-After. Не включать ожидаемые 429
в эти сценарии с порогом ошибок < 1%.

Документация k6: [arrival rate](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-arrival-rate/),
[пороги](https://grafana.com/docs/k6/latest/using-k6/thresholds/),
[пропущенные итерации](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/dropped-iterations/).
