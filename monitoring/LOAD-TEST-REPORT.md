# Отчёт о нагрузочном тестировании Shop API

19 ноября 2026 года, UTC+7. На локальном Docker-стенде смешанный сценарий выдержал
**около 160 HTTP-запросов/с на плато**. За прогон обработано **68 333 запроса**,
p95 составил **42 мс**, p99 — **73 мс**. HTTP-ошибок и пропущенных итераций не было.

## Условия

- Один экземпляр приложения на Java 21 и Spring Boot, PostgreSQL 18, k6 2.0.0,
  Prometheus 3.5.0. Контейнеру приложения выделено до 2 CPU и 1 ГБ памяти,
  Java heap ограничен 512 МБ. Максимальный размер пула HikariCP — 10 соединений.
- Начальное наполнение каталога — 20 категорий и 500 блюд. При подготовке каждого
  прогона создавались 20 пользователей. Заказы накапливались в тестовой БД, объём
  истории перед каждым прогоном отдельно не фиксировался.
- Сценарий `mixed` выполняет 70% итераций чтения каталога, 20% оформления заказа
  (запись, чтение заказа и истории) и 10% входа. Ограничение частоты входа и
  регистрации отключено в отдельной конфигурации нагрузочного стенда.
- `Rate` задаёт целевые итерации в секунду. В смешанном сценарии успешная
  итерация выполняет в среднем 1,4 HTTP-запроса. Фактический поток отслеживался
  по счётчику HTTP-запросов в Prometheus.

В таблице приведены метрики фазы нагрузки без HTTP-запросов подготовки. Среднее
за прогон включает разгон и снижение нагрузки. Для `baseline -Rate 125` замеры
Prometheus в 22:58, 22:59, 23:00 и 23:01 показали **156–163 HTTP-запроса/с**
без очереди за соединениями в эти моменты.

Пороги сценария для HTTP — p95 < 500 мс, p99 < 1 с и менее 1% ошибок. Для
сценариев — p95 < 1,5 с и менее 1% неуспешных итераций. Пропуски итераций
не допускаются. Три контрольных прогона прошли пороги. Стресс-тест превысил
пороги задержек и пропусков. Из 90 060 запланированных итераций 31 653
(35,1%) не стартовали после исчерпания свободных виртуальных пользователей.
Нулевая доля HTTP-ошибок относится к отправленным запросам.

## Где выросли задержки

На разгоне стресс-теста при фактических ~182 запросах/с общий серверный p95
составлял ~39 мс в минутном окне. Когда 30-секундное окно показало
~217 запросов/с, p95 отдельных маршрутов достиг 640–970 мс. Это наблюдения
на разгоне с разными окнами агрегации. Устойчивый максимум ими не измерен.

| Метрика Prometheus | 22:47:40 | 22:49:00 |
| --- | ---: | ---: |
| Потоки в очереди за соединением | 0 | 85 |
| Среднее время получения соединения за минуту | 0,1 мс | 359 мс |
| Среднее время удержания соединения за минуту | 6,5 мс | 43 мс |
| Загрузка CPU процесса Java (`process_cpu_usage`) | 76% | ≈100% |

Очередь HikariCP была измеримым источником задержки. Одновременно выросла загрузка
Java и увеличилось время удержания соединений. Это время включает работу приложения
внутри транзакций. Метрики пула сами по себе не устанавливают, замедлились ли SQL
запросы или приложение дольше держало соединения по другой причине.

## Воспроизведение

Команды, использованные на отдельном нагрузочном стенде из корня проекта:

```powershell
.\loadtest\run.ps1 -Profile baseline -Workload mixed -Rate 125 -SkipBuild
.\loadtest\run.ps1 -Profile stress -Workload mixed -Rate 50 -SkipBuild
```

На первом запуске опусти `-SkipBuild`, чтобы собрать образ. Для сравнения
прогонов зафиксируй ресурсы контейнеров и начальный объём истории заказов.
Запросы RPS, задержек и метрик пула есть в [инструкции по мониторингу](README.md).

Локальные журналы k6 в `loadtest/results/`, по порядку строк таблицы:
`20261119-221946-baseline-mixed.log`, `20261119-223236-baseline-mixed.log`,
`20261119-225424-baseline-mixed.log` и `20261119-224139-stress-mixed.log`.

## Повторные замеры после оптимизаций

21 ноября 2026 года, UTC+7. Повторили смешанный сценарий на локальном стенде с
лимитом приложения в 2 CPU. Сначала включили Redis для каталога, затем добавили
пагинацию истории заказов и индекс PostgreSQL. Сравнивались одинаковые профили
стресс-теста, по одному прогону на вариант. Начальный объём данных между прогонами
не фиксировался.

| Стресс-тест `-Rate 50` | Без Redis | Redis | Redis и пагинация |
| --- | ---: | ---: | ---: |
| Средний поток за прогон, HTTP-запросов/с | 124,6 | 130,7 | 135,7 |
| HTTP p95 за прогон | 1,11 с | 1,39 с | 1,29 с |
| p95 списка категорий | 1,08 с | 150 мс | 169 мс |
| p95 списка блюд | 1,08 с | 149 мс | 167 мс |
| Медиана запроса истории заказов | 96,6 мс | 114 мс | 17 мс |
| Пропущено итераций | 31 653 | 28 531 | 26 211 |

После обеих оптимизаций запустили `baseline -Rate 160` с Redis. По 16 точкам
Prometheus на плато с шагом 15 секунд фактический поток был **200–213 HTTP-запросов/с**,
в среднем **206 HTTP-запросов/с**. За весь прогон k6 обработал **87 365 запросов**
без HTTP-ошибок. HTTP p95 — **77 мс**, p99 — **451 мс**. k6 пропустил **54 из
62 459 итераций (0,086%)**. Задержки уложились в пороги, но критерий нулевых
пропусков не выполнен.

```powershell
.\loadtest\run.ps1 -Profile baseline -Workload mixed -Rate 160 -Redis
```
